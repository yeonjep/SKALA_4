# Day 1 실습 보고서: 간이 로그인 검증 프로그램 & Gradle 빌드

**SKALA 4반 박연제**

Map<String, String>을 메모리 DB로 사용하는 간이 로그인 검증 프로그램(App.java)의 코드 구조를 분석하고, Gradle을 이용해 프로젝트를 빌드·실행하는 과정을 진행함. 빌드 과정에서 발생한 트러블슈팅 사례를 정리하고, 해당 코드를 실제 서비스에 적용할 경우의 문제점과 개선 방향까지 함께 정리함.

## Chapter 1. 실습 목표와 진행 절차

### 1. 실습 목표

> 요약: Map<String, String>을 메모리 DB로 사용해 아이디·비밀번호를 평문으로 저장하고, 사용자가 입력한 값과 비교해 로그인 성공 여부를 판별하는 콘솔 기반 Java 프로그램의 코드 구조를 이해하고, Gradle을 이용해 실행 가능한 JAR로 빌드·실행해보는 것

### 2. 진행한 절차

1. App.java의 package·db 필드·static 초기화 블럭·main() 로직 등 코드 구성 요소 분석
2. package 선언(com.example.auth)과 실제 프로젝트 폴더 구조 일치 여부 확인
3. 프로젝트 최상위 폴더에서 `./gradlew clean build`로 JAR 빌드 진행
4. `java -jar app/build/libs/app.jar`로 생성된 JAR 실행 및 로그인 검증 동작 확인
5. 빌드·실행 과정에서 발생한 오류 4건 트러블슈팅 진행

### 3. 결과

App.java 코드 구조와 Gradle 빌드 흐름을 이해하고, JAR 빌드부터 실행까지 정상 완료함. 과정 중 gradlew 실행 위치 오류, package 선언 불일치, 오래된 테스트 파일, Manifest 누락 등 4건의 문제를 겪었고, 모두 해결하여 최종적으로 로그인 검증 프로그램이 정상 동작하는 것을 확인함.

## Chapter 2. App.java 코드 분석

### 1. package·import

package com.example.auth;로 선언됨. 이 파일은 반드시 `.../src/main/java/com/example/auth/` 경로에 위치해야 함. java.util 패키지에서 HashMap, Map, Scanner를 가져와 사용함.

### 2. static 필드 db

Map<String, String> 형태로 "아이디 - 비밀번호" 쌍을 저장함. 실제 DB를 대체하는 메모리 저장소 역할을 함.

### 3. static 초기화 블럭

클래스가 처음 메모리에 로드될 때 단 한 번 자동 실행됨. alice·bob 두 계정을 미리 등록해 둠.

### 4. main() 로직

Scanner로 아이디·비밀번호를 입력받아 trim()으로 공백을 제거함. containsKey()로 존재 여부를 확인한 뒤, equals()로 비밀번호를 평문 비교하여 결과를 출력함.

### 5. 파일 구조와의 관계

실제 프로젝트 폴더 구조와 위 코드는 다음과 같이 연결됨.

```
login_server/                          ← 최상위 (gradlew 위치)
├── gradlew, settings.gradle
└── app/                                ← 서브프로젝트
    ├── build.gradle                    ← mainClass='com.example.auth.App'
    └── src/main/java/com/example/auth/App.java
```

package 선언(com.example.auth)이 실제 폴더 경로와 정확히 일치해야 하며, build.gradle의 application.mainClass 값도 이와 동일해야 정상적으로 빌드·실행됨.

## Chapter 3. 빌드 트러블슈팅과 실제 서비스 적용 시 문제점

### 1. Gradle 빌드 트러블슈팅

**1. gradlew 실행 위치 오류**

- 문제: app 폴더 안에서 ./gradlew 실행 → "no such file or directory"
- 해결: gradlew는 프로젝트 최상위 폴더에만 존재함 → 최상위 폴더로 이동 후 실행

**2. package 선언 불일치**

- 문제: package login_server; (프로젝트 생성 시 자동 생성된 기본값) → "declared package does not match" 에러
- 해결: 파일의 실제 위치(com/example/auth)에 맞춰 package com.example.auth;로 수정

**3. 오래된 테스트 파일로 인한 컴파일 실패**

- 문제: 자동 생성된 AppTest.java가 삭제된 예전 App 클래스를 참조 → cannot find symbol 에러
- 해결: 실습에 사용하지 않는 기본 테스트 파일(AppTest.java) 삭제

**4. JAR 실행 시 Manifest 누락**

- 문제: java -jar 실행 시 "jar에 기본 Manifest 속성이 없습니다" 에러
- 해결: build.gradle의 application.mainClass를 com.example.auth.App으로 수정 후 재빌드

### 2. 보안상의 문제

- 비밀번호 평문 저장: db.put("alice", "pass1234")처럼 비밀번호를 암호화하지 않고 그대로 저장 → 코드나 메모리 유출 시 즉시 노출
- 평문 비교 방식의 인증: db.get(id).equals(pw)로 해시가 아닌 원문끼리 직접 비교 → 해싱·솔팅 미적용
- 무차별 대입 공격 방어 부재: 로그인 시도 횟수 제한·계정 잠금 정책 없음
- 인증 상태 유지 수단 없음: 로그인 성공 후에도 세션·JWT 등의 토큰 미발급 → 이후 요청에서 로그인 여부 확인 불가

### 3. 데이터 관리의 문제

- 휘발성 저장소: HashMap은 메모리에만 존재 → 프로그램 종료 시 모든 회원 데이터 소멸
- 영속성 부재: 파일·실제 DB 미저장 → 재시작 시 alice·bob 외 신규 가입자 전부 복구 불가
- 동시성 미고려: 다중 사용자 동시 접근 처리 없음 → 멀티스레드 환경에서 데이터 정합성 붕괴 가능
- 확장성 부족: 데이터가 단일 프로세스 메모리에만 존재 → 서버 다중화 시 서버마다 데이터 별도 존재

### 4. 개선 방향

- BCrypt 등 해시 알고리즘 적용해 비밀번호 암호화 저장
- MariaDB 등 실제 DB와 연동해 데이터 영속적으로 관리
- JWT 기반 인증 토큰 도입해 로그인 상태 유지
